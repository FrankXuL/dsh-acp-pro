## 实际

选择 codex-acp 路由开新会话后，会话里出现一条 **failed** 工具调用卡片，内容为：

```
[codex-acp] MCP server `context-mode` was not started, because the Codex config already defines
an MCP server with this name. Codex uses its own entry, or no server if that entry is disabled.
```

即 dsh 侧配置的 `context-mode` 没有被交给 codex，会话里表现为一个启动失败。

## 期望

正常使用——不该出现失败态的启动告警；如果这个 server 本来就由 Codex 自己那份配置提供，
用户也不该被告知「失败」。

## 复现步骤

1. dsh 里配置了 `context-mode` 这个 MCP server（dsh 侧 `serverName`）。
2. `~/.codex/config.toml` 的 `[mcp_servers.*]` 里也有同名条目 `context-mode`。
3. 选 codex-acp 路由开一个新会话。

已知频率：只要两边同名就必现，不是偶发。

1. **不是启动失败，是上游主动按名去重。** codex-acp 在 `session/new` 时把请求里的 MCP server 与
   Codex 自身配置（`configRead({ includeLayers: true })` 汇总的 `mcp_servers` 键名）比对，
   同名的丢进 `skippedMcpServers`（`dist/index.js:40290-40293`），之后既不 `startServer`
   也不进 `awaitMcpServerStartup`。
2. **「未启动」不等于「不可用」。** 服务由 Codex 自己那条提供；只有那条被禁用/缺失时才真的少能力。
3. **呈现口径是问题所在：** `McpStartupReporter.skipped()` 复用真实失败的 `failure()` 构造器
   （`dist/index.js:37945-37950`），产出 `status:'failed'`、`kind:'other'`、
   `title: mcp__<server>__startup`；`publish()` 把 skipped 与真实 failures 拼进同一数组发出去
   （`dist/index.js:38092`）。协议层没有「跳过」这个状态。
4. **本插件照实渲染：** failed 的 ACP `tool_call` 记成 `plugin:acp/tool-call`，
   客户端画成红色失败卡片（`src/host/service/acp-record-sink.ts:168`、`src/client/components/record-nodes.tsx`）。
5. **规模可能不止一条：** dsh 侧全量转发（`src/host/transport/acp-agent.ts:244`，
   `forwardMcp` 默认 `true`，见 `src/host/config/schema.ts:48`），本机 10 个 MCP serverName 与
   Codex 配置重名 8 个，每个重名都可能各报一条。

候选处置方向（未定，留给分诊）：

- 路由侧 `forwardMcp: false`——代价是 Codex 侧只剩它自己配的那几个 MCP。
- 路由 `env` 设 `DISABLE_MCP_CONFIG_FILTERING=true`——代价是同名 server 会真的启动两份。
- 呈现侧把 `mcp__*__startup` 这类 `kind:'other'` 的 failed 记录降级成信息行——需先确认不掩盖真实失败。
