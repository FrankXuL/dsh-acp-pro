# 04: 轨迹契约：插件记录进原生轨迹的可行性边界

Type: research

Status: resolved

## Question

要让 ACP 的工具 / 计划 / 权限出现在原生轨迹视图里，插件侧必须满足哪些精确契约？（AFK research 票，产出可执行契约，不写实现。）

## Answer

研究笔记：[`docs/design/acp-trajectory-parity-contract-2026-10-28.md`](../../docs/design/acp-trajectory-parity-contract-2026-10-28.md)（555 行，逐条 `file:line`，全部引自 rc.2 `687f282e`，未改源码）。

### 一、结论（三档）

**可做**
1. 新增 `target: 'trajectory'` 的 Definition，让 ACP tool-call 以 `{ kind: 'node', node: <tool-result 形状> }` 进轨迹 —— `trajectory-snapshot-builder.ts:233-237` 是唯一能把外部对象塞进 `eventNodes` 的通道。
2. **无需注册 view builder**：`target: 'trajectory'` 的 builder 已由上游注册（`trajectory-snapshot-builder.ts:303-320`）；插件重复注册会抛（`view-registry.ts:12-15`）。
3. **与现有三个 chat Definition 并存无需改 chat 侧**：现有三份未返回 `exclusive`（已复核 `src/client/conversation/records.ts` 只有 `target: 'chat'`，无 claim），`exclusive` 只在同 target 内互斥（`conversation.ts:11-20`、`assembler.ts:519-536`）。
4. usage pill 与 ContextMeter **在 ACP 会话里应已正确工作，不需要补投影字段**：本插件在 `acp-adapter.ts:1369` 发 usage chunk，`usageDelta` 总是给 `inputTokens/outputTokens/totalTokens`（`chunk-translator.ts:104-119`），满足 `turn-usage.ts:104-118` 对 `totalTokens` 的要求。

**不可做**
1. 插件自带新 contribution kind —— `TrajectoryContribution` 是 8 成员封闭 union（`trajectory-contract.ts:23-58`），同文件的 `ConversationViewSnapshotMap`/`SlotMap` 可 merge，**唯独 contribution kind 不能**。
2. 导入 `trajectoryNode` —— 非 barrel 导出（已复核 `ui-trajectory/src/client/index.ts:31-41` 只导出类型），`./client` 不含它，运行时 module table 解析不到即 throw。
3. 一个 Definition 同时服务 `chat` + `trajectory` —— 契约注释写 `Sole view target`（`conversation.ts:215`），`buildNode` 单值比对（`assembler.ts:906`）。
4. **plan / permission 进轨迹** —— 无对应 contribution kind，`ConversationNode` 也无对应成员。硬塞成 `tool-result` 技术上不崩，但把计划伪装成工具结果，违反 `AGENTS.md` 的 truthful 要求，**明确否决**。
5. 让轨迹显示 ACP 侧 system prompt —— 需伪造 `system/message`，会污染 header `change` 计算，否决。

**需要上游**
1. 放宽 `ToolResultNode.args` 为可选，或把 `PartialArguments` 导出到 client module table（消除类型逃逸）。
2. 开放 `TrajectoryContribution` 扩展点（plan/permission 才能不伪装地进轨迹）。
3. 开放 `DetailTab` 或给 `callSchemas` 注入点（schema tab 才能有真数据）。
4. 明确 `inspectCall` 的 target 优先级（现在是「第一个可见的 inspection target」）。

### 二、两处对原假设的更正（重要，已复核）

1. **ACP 会话确实有 `request/header`**。`AcpAdapter extends LlmAdapter`（`src/host/service/acp-adapter.ts:244`）经 `ctx.llm.registerAdapter`（`src/host/apply.ts:225`）注册，agent-loop 与适配器无关，`request/header` 写在 `packages/core/agent-loop/src/agent.ts:637-650`。**插件不需要补 request-header contribution**；轨迹里的请求头显示的是 DSH 侧真实信封。真实缺口只有 ACP 进程内的 system prompt，不该伪造。
2. **`ConversationViewNodeRegistration` 在 harness 中不存在**（全仓 grep 0 命中）。真实机制是 `ConversationViewDefinition.toolCallFocus?`（`conversation.ts:319-324`）+ `apply.ts:394-401` 的 `inspectionTarget()` 取「第一个可见的 inspection target」——这是需要上游裁决的优先级问题。

### 三、最小贡献映射（定案）

- **新建 3 个 `target: 'trajectory'` 的 Definition**（tool-call / plan / permission 镜像），但**只有 tool-call 真能进轨迹**；技术最小闭环 = 1 个。
- `target` 值：字符串字面量 `'trajectory'`。
- 写法：`{ kind: 'node', node: <ToolResultNode 形状> }`，自建 7 字段信封；**不 import `trajectoryNode`、不注册 view、不返回 `exclusive`、只读 `plugin:acp/*` 不写任何 `tool/call`/`tool/result`** —— 本插件实测 grep 这些事件 0 命中，合规无需改动。
- 新 Definition 的 `kind` 必须与现有三个不同（`definition-registry.ts:49` 重复即抛）。

### 四、必须随实施记账的技术债

`ToolResultNode.args` 类型必填但运行时从不读取（`grep '\.args\b'` 只命中从 `previewMarkdown` 派生的展示文本，`summarizeCall` 只用 name/argsRaw）。可 `as unknown as ToolArgs` 逃逸，**必须记为技术债，并优先请上游放宽**。

### 五、三处落地前置检查

1. 在 rc.3 复核 union 与 exports（本文全为 rc.2）。
2. 补「未知 kind 不崩」回归测试（builder 末尾 `:269` 是无 `else` 的裸分支）。
3. 确认 `DetailTab` 在 ACP 场景的降级：`input`/`output`/`overview` 可用，`schema` 必现但空（降级为 `record.schemaUnavailable`），`timing` 可用，`raw`/`source`/`rendered`/`usage`/`options`/`diff` 天然不出现 —— **不需要处理，它们根本不会列出**。

定案：可做 = 新建 3 个 target:'trajectory' Definition（技术最小闭环 1 个，仅 tool-call），走 kind:'node' + tool-result 形状，不 import 上游内部 helper、不注册 view、只读 plugin:acp/*；不可做 = 自带新 contribution kind、plan/permission 进轨迹、伪造 system prompt；需要上游 4 项（args 放宽/contribution 扩展/DetailTab/schema 注入/inspectCall 优先级）。并更正两处原假设：ACP 确有 request/header；ConversationViewNodeRegistration 不存在。
