## 实际

## 已修复（2026-10-29，`/diagnosing-bugs` 走查）

**根因已由活体页面上的一手证据确认，不是纸面推断。**

### 证据链（真机 DSH，非源码推演）

1. **弹层计算值**：`.dsh-model-seat-panel` 的 computed `z-index` 是 **10005**——不是仓里的 1100。
   溯源到另一个插件注入的 `!important` 规则：
   `div[class*="_portal"], div[role="menu"], … { z-index: 10005 !important }`，
   其 `ownerNode.dataset.plugin` = `@wenbin_wb/dsh-bridge`。仓内 1100 被第三方 `!important` 覆盖。
2. **封顶实测**：在 body 上挂一个 `position:fixed;z-index:9` 的探针，`elementFromPoint` 判定
   **探针赢、弹层输**——尽管弹层自报 10005。原因：弹层祖先链上
   `kiGsTW_composerSeat { position:sticky; z-index:7 }` 建立了 stacking context，
   弹层的 10005 只在该 context **内部**排序；外部任何 ≥8 的层都能整体盖住这个 context。
3. **对照组**：DSH 原生 `ui-model-selection` 用 `createPortal(…, document.body)`
   （`ModelSelect.tsx:497`），`ModelSelect.module.css:93` 的 1100 才成立。
   → **本插件照抄了原生 z-index，没照抄它的 portal。** 这也解释了为什么单纯抬 z-index
   永远治不好：抬多少都关在 z=7 的盒子里。

### 修法（最小改动）

- `src/client/components/model-seat.tsx`：弹层渲染改为
  `open && anchor !== null && createPortal(<div …/>, document.body)`。
  弹层脱离座位子树，祖先不再是 stacking context，10005 回到全局层。
- `tsdown.config.ts`：`CLIENT_SEEDS` 补 `react-dom` / `react-dom/client`。
  **这是修法的前置条件而非顺手改动**：用了 `createPortal` 就必须在运行时拿到 react-dom；
  不加种子会把整整第二份 ReactDOM 打进 bundle（实测 190KB → 320KB），
  其 portal 容器与事件根会和 shell 的分家。DSH 的
  `packages/client/web/src/platform.ts` 里本来就把两者列为种子。
- 文档同步：`docs/dsh-plugin-dev/02-plugin-structure.md`、
  `05-build-test.md` 的种子清单补上 `react-dom`。
- 顺手清死代码（满足仓内「scheduled split 只能变小」棘轮，423 行基线）：
  删除无人引用的 `FAVORITES_KEY`、3 个未使用的类型导入，合并重复的 react 导入。

### 本次修复引入的**已知副作用**（如实记录，未处理）

**Tab 焦点顺序变了**：弹层现在是 body 的最后一个子节点，键盘焦点序从
「trigger → 弹层」变成 trigger 之后隔约 10 个焦点元素才到弹层。
原生选择器没有这个问题（它自己也 portal，但它在 portal 后显式 `focus()` 到菜单内）。
本插件的弹层**从来就没有开菜单时主动移焦的逻辑**，所以这不是新破的，而是既有缺口
被 portal 放大得更明显。是否补「开菜单即聚焦」属于交互决策，不在本单范围——
建议按规格票「来源 tab 的交互规格」里已定的双栏键盘模型单独开单。
